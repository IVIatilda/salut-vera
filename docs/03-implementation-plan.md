# План реализации MVP

Дата: 15 октября 2026

## Принятые допущения

- Первый клиент — адаптивное веб-приложение.
- Архитектура клиента — PWA с local-first хранением и последующей синхронизацией.
- Первый язык — русский.
- Приложение персональное; совместная работа не входит в MVP.
- На первом этапе важнее надежная предметная модель и основные ритуалы, чем сложная
  геймификация.
- Основной язык всего стека — JavaScript.

## Технологический стек

- React + Vite — клиентское приложение на JavaScript.
- IndexedDB — локальная база данных; слой доступа изолирован для будущей синхронизации.
- Service Worker + Web App Manifest — установка PWA и работа офлайн.
- Node.js — будущий сервер синхронизации.
- PostgreSQL — предполагаемое облачное хранилище после проектирования протокола
  синхронизации.
- Vitest — модульные тесты; Playwright — будущие сквозные тесты.

Нативное мобильное приложение не требуется для проверки MVP. При необходимости PWA
можно упаковать через Capacitor; переход к React Native стоит рассматривать только при
появлении требований, которые невозможно надежно реализовать через веб-платформу.

## Этап 1. Каркас продукта

- выбрать стек и способ авторизации;
- создать дизайн-токены и адаптивную оболочку;
- реализовать навигацию и пустые состояния;
- создать схему базы данных и миграции;
- реализовать сферы жизни с описанием идентичности, навыки и проекты.

Результат: пользователь входит в приложение и может настроить базовую структуру жизни.

## Этап 2. Задачи и планирование

- входящие и быстрый ввод;
- CRUD задач, подзадач и проектов;
- представления «Сегодня», «Предстоящие», «Без даты»;
- важность, срочность и происхождение задачи;
- календарное планирование;
- сценарий выгрузки и разбора входящих.

Результат: пользователь выгружает дела, разбирает их и составляет реалистичный план.

## Этап 3. Фокус и учет времени

- Pomodoro и пользовательские интервалы;
- связь с задачей;
- устойчивость таймера к перезагрузке страницы;
- записи времени;
- обычная и целенаправленная практика;
- базовые отчеты по проектам и навыкам.

Результат: затраченное время учитывается без ручного пересчета.

## Этап 4. Привычки

- создание привычки по четырем законам изменения поведения;
- расписание и журнал выполнения;
- минимальная версия и восстановление после пропуска;
- календарь регулярности;
- связь со сферами и навыками.

Результат: приложение поддерживает формирование системы, а не только серию отметок.

## Этап 5. Ежедневные ритуалы и дневник

- утренний пошаговый ритуал;
- вечерний пошаговый ритуал;
- эмоции, благодарности, маленькие победы и дневниковый текст;
- задачи на сегодня и завтра внутри ритуалов;
- частичное сохранение и продолжение ритуала.

Результат: день начинается с реалистичного плана и заканчивается осмысленным обзором.

## Этап 6. Еженедельный обзор и развитие

- мастер еженедельного обзора;
- загрузка и открытые контуры;
- баланс и заброшенные сферы;
- вехи навыков;
- карта сфер, идентичностей и собственных/чужих планов;
- прозрачные рекомендации по изменению среды.

Результат: пользователь завершает обзор с планом следующей недели и одним конкретным
изменением системы.

## Этап 7. Проверка MVP

- модульные тесты расчетов и повторений;
- интеграционные тесты таймера и ритуалов;
- сквозные тесты ключевых сценариев;
- проверка адаптивности, клавиатурной навигации и контрастности;
- экспорт, удаление и восстановление данных;
- пилотное тестирование на небольшой группе пользователей.

## Первые сквозные сценарии для реализации

1. Быстро записать мысль → разобрать входящие → создать задачу → запланировать.
2. Открыть утренний ритуал → выбрать три результата → начать первую фокус-сессию.
3. Завершить фокус-сессию → записать результат → увидеть время в задаче и навыке.
4. Отметить привычку → пропустить следующий день → вернуться через минимальную версию.
5. Открыть вечерний ритуал → перенести задачу → отметить эмоции и благодарность.
6. Провести еженедельный обзор → заметить перегрузку → разгрузить следующую неделю.

## Решения, которые нужно принять до написания production-кода

- Веб-приложение или приоритет нативного мобильного клиента.
- Облачное хранение, локальное хранение или режим local-first с синхронизацией.
- Нужна ли регистрация в первой тестовой версии.
- Требуется ли шифрование дневниковых записей на стороне клиента.
- Нужны ли интеграции с Google Calendar или Apple Calendar в ранней версии.

Эти решения влияют на архитектуру, безопасность и стоимость разработки; выбирать их
неявно при создании первого интерфейса не следует.
